# TalkTracker 웹 서버 모드 구현 계획

## 1. 목적과 범위

분석 성능이 좋은 Linux GPU PC에 TalkTracker를 한 번 설치하고, 같은 네트워크의 다른 PC에서는 웹 브라우저로 녹음 파일을 올려 분석을 요청할 수 있게 한다. 분석 모델·업로드 파일·결과 파일은 모두 TalkTracker 서버 PC 안에만 둔다.

이 계획은 현재 데스크톱 GUI를 없애거나 바꾸지 않는다. Tkinter GUI와 웹 서버는 같은 분석 엔진을 공유하되, 각각 별도 실행 방식으로 유지한다.

첫 구현 범위는 다음과 같다.

- 브라우저에서 음성 파일 업로드와 Whisper 프로필 선택
- 작업 생성, 대기·진행·완료·실패·중단 상태 확인
- 화자 타임라인과 전사 진행 상태 표시
- 완료 또는 중단된 작업의 Markdown 결과 다운로드
- 한 번에 하나의 분석 작업만 실행하는 대기열
- 로컬 네트워크 또는 SSH 터널을 통한 제한된 접근

실시간 마이크 전사, 여러 사용자의 계정 관리, 인터넷 공개 서비스, 작업 여러 개의 동시 GPU 실행은 첫 범위에서 제외한다.

## 2. 목표 구성

```text
다른 PC의 웹 브라우저
  └─ 음성 파일 업로드 · 모델 선택 · 상태/결과 확인
                 │ HTTP / 서버 전송 이벤트
                 ▼
TalkTracker 웹 서버 (분석용 Linux GPU PC)
  ├─ API와 웹 화면
  ├─ 작업 대기열 (기본 동시 실행 1개)
  ├─ 기존 AnalysisEngine
  │   ├─ Nemotron 화자 분리
  │   └─ Whisper 전사
  └─ outputs/jobs/<작업 ID>/ 원본·결과·진단 로그
```

기존 `AnalysisEngine`은 파일 경로, 진행 콜백, 화자 분리 콜백, 중단 콜백을 이미 받는다. 웹 서버는 이 콜백을 작업 상태 저장소에 연결하고, 브라우저는 상태 API 또는 서버 전송 이벤트(SSE)로 이를 읽는다. Tkinter 화면의 큐 처리 코드는 웹 서버의 작업 관리자로 옮기되, 분석 로직 자체는 중복 구현하지 않는다.

## 3. 실행 환경과 파일 보관

- 처음에는 Linux GPU PC를 서버 대상으로 지원한다. 설치·모델 다운로드는 기존 Linux 스크립트를 그대로 사용한다.
- 웹 서버 전용 실행 진입점으로 `scripts/linux/Run-Web.sh`를 추가한다. GUI 실행 스크립트와 별개로 둔다.
- 업로드 파일, 분석 결과, 상태 메타데이터는 `outputs/jobs/<UUID>/` 아래에 보관한다. 모델 폴더와 Git으로 관리하는 소스 폴더에는 업로드 파일을 넣지 않는다.
- 작업이 끝난 뒤 보관 기간(기본 7일)을 지난 파일은 서버가 정리할 수 있게 한다. 자동 삭제 전에는 웹 화면과 문서에 보관 기간을 명시한다.
- 모델 준비와 CUDA 확인은 서버 시작 시 한 번 확인한다. 분석 요청마다 모델을 다운로드하거나 설치 스크립트를 실행하지 않는다.

## 4. API와 화면의 최소 동작

| 기능 | API 예시 | 웹 화면 동작 |
| --- | --- | --- |
| 서버 상태 | `GET /api/health` | 모델·CUDA·대기열 상태 표시 |
| 작업 생성 | `POST /api/jobs` | 파일과 프로필을 전송하고 작업 ID 수신 |
| 작업 조회 | `GET /api/jobs/{id}` | 단계, 진행률, 처리 시각, 오류, 타임라인 표시 |
| 진행 수신 | `GET /api/jobs/{id}/events` | SSE로 상태 변경을 즉시 반영, 연결 실패 시 조회 방식으로 전환 |
| 중단 | `POST /api/jobs/{id}/cancel` | 대기 작업은 즉시 취소하고, 실행 작업은 기존 중단 콜백으로 전달 |
| 결과 받기 | `GET /api/jobs/{id}/result.md` | Markdown 파일 다운로드 또는 브라우저 미리보기 |
| 파일 삭제 | `DELETE /api/jobs/{id}` | 결과 확인 후 업로드·결과를 함께 삭제 |

### 로컬 AI 결과 만들기 — 구현 완료

웹 서버를 `127.0.0.1` 또는 `localhost`에 바인딩하면, 같은 웹 화면에서 서버 PC 또는 신뢰하는 사설망의 OpenAI 호환 LLM 서버를 연결할 수 있다. 브라우저의 API 키 입력을 보호하기 위해 `--host 0.0.0.0`으로 내부망에 직접 공개한 웹 서버에서는 이 연결 패널을 숨긴다.

분석 뒤 원본 전사는 자동 보존한다. 사용자는 다듬은 대화와 요약을 하나 또는 둘 다 선택해 만들고, 대화 목적·배경과 화자별 표시 이름·역할을 현재 요청에만 제공할 수 있다. 웹 화면은 AI 단계·경과 시간·중단 상태를 표시하고, 원본 전사·다듬은 대화·요약을 전환해 확인한다. 각 결과는 별도 Markdown 문서로 내려받으며, 나중에 요약을 추가해도 기존 다듬은 대화는 유지한다.

| 기능 | API | 동작 |
| --- | --- | --- |
| AI 연결 정보 | `GET /api/local-llm` | API 키 없이 최근 성공 주소·선택 모델·연결 상태를 읽음 |
| 모델 조회·연결 확인 | `POST /api/local-llm/models`, `POST /api/local-llm/verify` | 모델 목록 조회와 짧은 생성 요청으로 실제 사용 가능 여부 확인 |
| AI 결과 만들기 | `POST /api/jobs/{id}/ai-refinement` | 다듬은 대화·요약 요청을 시작하고 기존 AI 결과와 병합 |
| AI 상태·중단 | `GET /api/jobs/{id}`, `POST /api/jobs/{id}/ai-refinement/cancel` | AI 단계·경과 시간·오류를 읽고 실행 중인 요청을 취소 |
| 결과별 문서 | `GET /api/jobs/{id}/ai-results/{kind}.md` | 원본 전사·다듬은 대화·요약을 각각 다운로드 |

작업 생성 API는 지원하는 파일 형식·최대 파일 크기·허용된 Whisper 프로필만 받는다. 클라이언트가 임의의 서버 경로나 모델 이름을 전달하도록 만들지 않는다.

## 5. 작업 관리 원칙

1. 요청을 받으면 파일을 작업별 폴더에 저장하고 `queued` 상태로 기록한다.
2. 단일 워커가 FIFO 순서로 하나의 작업만 꺼내 `AnalysisEngine.analyze()`를 호출한다.
3. 진행 콜백은 단계·진행률·처리한 녹음 시각을 작업 상태에 기록한다.
4. 화자 분리 콜백은 화자 타임라인 미리보기를 기록해 전사가 끝나기 전에도 화면에 보여 준다.
5. 중단 요청은 대기 중이면 즉시 `cancelled`로, 실행 중이면 기존 `should_cancel` 콜백으로 전달한다.
6. 완료·중단·실패 상태에서는 결과 경로 또는 사람이 읽을 수 있는 오류와 기존 진단 로그 경로를 보관한다.

기본 동시 실행 수는 반드시 1개다. Nemotron과 Whisper가 CPU·GPU 메모리를 크게 사용하므로, 여러 작업을 동시에 실행하면 속도 저하·VRAM 부족·결과 혼동이 발생할 수 있다. 병렬 실행은 GPU 메모리와 장시간 녹음으로 검증한 뒤 별도 설정으로만 허용한다.

## 6. 보안과 네트워크 기본값

- 기본 수신 주소는 서버 PC 내부 전용 `127.0.0.1`로 한다.
- 다른 PC에서 쓰려면 SSH 터널을 우선 안내한다. 이 경우 서버 포트를 네트워크에 직접 열지 않아도 된다.
- 로컬 네트워크에 직접 열기는 명시적 옵션으로만 제공하고, 임의로 생성한 접근 토큰을 요구한다.
- 외부 인터넷에 직접 공개하는 구성은 첫 구현 범위에서 지원하지 않는다. 필요할 경우 TLS 역방향 프록시, 강한 인증, 방화벽, 업로드 제한을 별도 설계한다.
- 업로드 이름은 서버 파일명으로 그대로 쓰지 않고 작업 ID 기반 저장 이름을 사용한다. 경로 이동 문자열을 차단하고, 파일 크기 제한과 보관 기간을 적용한다.
- 상태·결과 API는 해당 작업의 접근 토큰 또는 서버 공통 토큰을 검사한다. 작업 ID만 아는 다른 사용자가 파일을 읽거나 중단할 수 없어야 한다.

## 7. 구현 단계

### 단계 A — 분석 엔진과 작업 객체 분리

- 웹과 GUI에서 공통으로 쓸 `AnalysisJob`·`JobStore`·`AnalysisWorker`를 추가한다.
- 현재 GUI의 진행 이벤트·중단 처리를 공통 작업 상태로 연결한다.
- 파일별 작업 폴더와 Markdown 결과 저장 함수를 만든다.
- 단위 테스트로 정상 완료, 모델 누락, 분석 오류, 대기 중 취소, 실행 중 취소를 확인한다.

완료 기준: GUI를 변경하지 않고도 Python 코드에서 작업 하나를 생성·조회·중단할 수 있다.

### 단계 B — HTTP API와 서버 실행

- FastAPI와 Uvicorn 기반의 웹 서버 모듈을 추가한다.
- 상태, 업로드, 작업 조회, 취소, 결과 다운로드 API를 구현한다.
- `Run-Web.sh`와 서버 설정 예시를 추가한다.
- 서버 시작 시 모델·CUDA 준비 상태를 `health` API로 제공한다.

완료 기준: 같은 PC의 브라우저 또는 `curl`로 음성 파일을 올려 결과 Markdown을 받을 수 있다.

### 단계 C — 브라우저 화면과 진행 표시

- 파일 선택, 프로필 선택, 업로드, 대기열 순서, 진행률, 처리한 녹음 시각을 표시한다.
- SSE로 화자 타임라인·단계·오류·완료 상태를 갱신하고, 연결이 끊기면 상태 조회로 복구한다.
- 완료 결과를 화면에서 읽고 Markdown으로 내려받게 한다.

완료 기준: 다른 PC의 브라우저에서 별도 파일 전송 명령 없이 업로드부터 결과 저장까지 마칠 수 있다.

### 단계 D — 원격 사용 검증과 운영 보완

- SSH 터널을 통한 원격 브라우저 접근을 검증한다.
- 토큰 인증, 업로드 크기 제한, 보관 기간 정리, 디스크 부족 안내를 검증한다.
- GPU Linux PC에서 Small·Turbo·Large-v3와 짧은·긴 녹음의 대기열 동작을 기록한다.

완료 기준: 작업 취소·서버 재시작·업로드 실패·GPU 오류에서도 다른 작업과 기존 결과가 손상되지 않는다.

## 8. 검증 기준

- 업로드한 파일이 다른 작업의 파일과 섞이지 않는다.
- 작업 상태가 `queued`, `running`, `completed`, `cancelled`, `failed` 중 하나로 일관되게 끝난다.
- 브라우저 진행 표시와 `AnalysisEngine`의 실제 단계·처리 시각이 일치한다.
- 결과 다운로드 파일이 데스크톱 GUI의 Markdown 저장 결과와 같은 화자·시간·전사 내용을 가진다.
- GPU 오류와 불완전한 모델 오류가 원인을 숨기지 않고 작업 상태와 진단 로그에 남는다.
- 기본 설정의 서버는 외부 네트워크에 노출되지 않는다.

## 9. 구현 전 확인할 결정

- 첫 서버 지원 운영체제를 Linux GPU 전용으로 확정할지
- 작업 결과 기본 보관 기간과 최대 업로드 파일 크기
- 로컬 네트워크 직접 접속을 첫 버전에서 열지, SSH 터널만 지원할지
- 작업별 접근 토큰과 서버 공통 토큰 중 어떤 방식으로 시작할지
- HTML 결과 다운로드를 첫 버전에 포함할지
