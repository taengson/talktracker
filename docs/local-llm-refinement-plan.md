# 로컬 LLM 전사 다듬기·요약 구현 계획

## 1. 목적

TalkTracker가 음성 분석으로 만든 **원본 전사 메시지**를 사용자가 실행 중인 로컬 LLM으로 보내, 사용자가 고른 결과를 만듭니다.

1. 원본 전사 메시지
2. 화자·시간 정보는 유지한 채 문장부호, 띄어쓰기, 오인식 표현을 읽기 좋게 다듬은 대화
3. 대화의 핵심 내용, 결정 사항, 할 일, 확인이 필요한 내용을 정리한 요약

음성 파일·원본 전사·AI 정리 결과는 기본적으로 PC 밖으로 전송하지 않습니다. LLM 서버도 같은 PC에서 실행하는 것을 첫 지원 범위로 합니다.

이 기능은 **Windows 데스크톱 GUI**와 **같은 PC의 브라우저에서 여는 로컬 웹 화면**에서 동일하게 사용할 수 있게 만든다. 두 화면은 같은 분석·LLM 정리 엔진을 사용하므로 결과와 동작 규칙이 다르지 않다.

## 2. 참고 구조와 적용 범위

연결 방식은 [agent-chat-desktop](https://github.com/taengson/agent-chat-desktop)의 기본 채팅 연결을 따른다.

- 사용자가 먼저 로컬 LLM 서버를 실행한다.
- TalkTracker는 OpenAI 호환 API의 `GET /v1/models`로 모델 목록을 읽고, `POST /v1/chat/completions`으로 요청한다.
- 서버 주소 끝의 `/v1` 유무를 앱이 정규화한다.
- API 키가 필요한 로컬 서버도 연결할 수 있게 하되, 키는 메모리에만 유지하고 파일·결과·로그에는 저장하지 않는다.
- 긴 생성은 스트리밍 응답으로 받고, 사용자는 언제든 중단할 수 있다.

다만 TalkTracker에는 채팅, 문서 첨부, 벤치마크 기능을 가져오지 않는다. 연결된 LLM은 화자 분석과 전사가 끝난 뒤, 사용자가 선택한 정리 작업에만 사용한다. 전사 결과를 다듬고 요약하는 데 필요한 연결·모델 선택·생성·저장만 구현한다.

### 첫 버전에서 제외하는 것

- TalkTracker가 LLM 서버나 LLM 모델 자체를 설치·실행·종료하는 기능
- 클라우드 API 및 인터넷상의 서버 연결
- LLM과 대화하는 별도 채팅 화면
- 원본 전사를 AI 결과로 자동 교체하는 동작
- LLM 서버가 보관한 최근 요청·작업·대화 기록을 조회하거나 화면에 표시하는 기능
- 자동 실행되는 최근 기록·장기 대화 보관 기능

LLM 가중치는 기존 `models/` 폴더에 복제하지 않는다. 사용자가 선택한 로컬 LLM 서버가 자신의 모델과 실행 환경을 관리하고, TalkTracker는 로컬 API 클라이언트 역할만 맡는다.

TalkTracker도 AI 요청·응답의 별도 최근 기록 화면을 만들지 않는다. 처리 중에는 현재 작업의 진행 상태만 표시하고, 완료 결과는 사용자가 필요할 때 명시적으로 Markdown으로 저장한다. 앱을 다시 실행했을 때 이전 AI 작업을 자동으로 불러오거나 목록으로 보여 주지 않는다. 이 원칙은 GUI와 웹 화면에 동일하게 적용한다.

## 3. 사용자 흐름

GUI와 웹 화면은 화면 형태만 다를 뿐, 아래 흐름과 결과 형식을 공통으로 사용한다.

### 3.1 로컬 AI 연결

1. 사용자가 자신의 PC 또는 신뢰하는 사설망에서 OpenAI 호환 로컬 LLM 서버를 실행한다.
2. TalkTracker 상단의 **로컬 AI 연결** 메뉴를 연다.
3. 서버 주소를 입력하거나 마지막으로 사용한 로컬 주소를 확인한다.
4. **모델 불러오기**를 누르면 서버의 모델 목록을 읽고 모델 하나를 선택할 수 있다.
5. **연결 확인**은 짧은 요청으로 실제 생성까지 가능한지 확인한다.
6. 연결이 완료되면 메뉴 상태를 `로컬 AI 연결됨 · [모델 이름]`으로 표시한다.

같은 PC의 `localhost`, `127.0.0.1`, `[::1]`뿐 아니라 사용자가 지정한 사설망 LLM 서버의 IP 주소 또는 호스트 이름도 허용한다. 입력한 주소에 계정 정보, 쿼리 문자열, 조각 식별자가 들어 있으면 저장하거나 사용하지 않는다. 다른 PC의 서버를 선택한 경우에는 전사문과 안내 입력값이 그 서버로 전달될 수 있음을 연결 화면에서 분명히 알린다.

서버 주소와 마지막 선택 모델은 사용자 설정 영역에 저장할 수 있다. 연결 확인에 성공한 주소만 최근 연결 목록에 남기며, 사용자는 주소 입력칸에서 이를 다시 고를 수 있다. API 키는 앱을 종료하면 사라지고, 여러 연결 프로필을 관리하는 기능은 첫 버전 범위에 넣지 않는다.

### 3.2 분석 결과 정리

1. 사용자가 음성 분석을 마치면 기존의 원본 전사와 화자 타임라인이 먼저 표시된다.
2. 결과로 받을 항목에서 `원본 전사 메시지`, `다듬은 대화`, `요약`을 하나 이상 고른다. 원본만 고르면 LLM 연결 없이 바로 결과를 만들 수 있다.
3. 다듬은 대화나 요약을 고른 경우에는 **대화의 목적·배경 안내**와 **화자 안내**를 입력할 수 있다. 배경 안내에는 회의 목적, 프로젝트명, 약어·고유명사를 적고, 화자 안내에는 분석에서 찾은 `화자 1`, `화자 2`마다 이름이나 역할을 적는다. 입력 내용이 구체적일수록 전사 보정과 요약의 정확도가 좋아진다는 안내를 입력칸 바로 아래에 표시한다.
4. 로컬 AI가 연결된 상태에서 **AI로 결과 만들기**를 누르면, 선택한 AI 결과만 생성한다.
5. 진행 중에는 `AI가 대화를 다듬고 있습니다 · 전체 전송 중 · 경과 00:02:14` 또는 `컨텍스트 한도로 4개 구간으로 나누어 정리 중 · 3/4`처럼 현재 상태를 표시하며, **중단** 버튼을 제공한다.
6. 완료 후 결과 영역에는 사용자가 고른 `원본 전사 메시지 / 다듬은 대화 / 요약`만 표시한다. 원본 전사 메시지와 다듬은 대화는 같은 시간·순서·`(화자 N)` 표기를 유지하므로, 문서를 번갈아 보며 어떤 문장이 어떻게 바뀌었는지 확인할 수 있다. 다듬은 대화와 요약은 여러 요청으로 처리됐더라도 각각 하나의 완성된 결과로 합쳐 보여 준다.
7. 저장할 때도 사용자가 고른 항목만 Markdown으로 내보낸다. AI 처리 중단 시에는 완료된 다듬기 구간만 표시하고, 선택했지만 끝나지 않은 요약은 `미완료`로 명시한다.

AI 정리는 기존 음성 분석 단계에 자동으로 끼워 넣지 않는다. 긴 오디오에서 이미 시간이 걸리는 화자 분리·전사가 끝난 뒤 사용자가 필요할 때만 실행하므로, LLM이 준비되지 않았거나 느려도 기본 분석 기능은 영향을 받지 않는다.

### 3.3 대화의 목적·배경 및 화자 안내

입력란의 이름은 **대화의 목적·배경 안내**로 한다. 이 입력은 선택 사항이지만, 빈 입력란에는 다음과 같이 안내한다.

> 회의 목적, 논의 주제, 참여자 역할, 프로젝트명, 약어·고유명사를 자세히 적으면 전사 보정과 요약이 더 정확해집니다. 입력한 내용도 로컬 AI 서버에만 전달됩니다.

안내문은 전사를 바꾸는 정답 사전이 아니다. LLM이 전사문에 없는 사실을 만들어 내지 않도록, 배경 정보는 문맥 이해와 용어 표기에만 쓰고 전사문을 우선하도록 프롬프트에 명시한다.

화자 타임라인이 만들어진 뒤에는 그 아래에 **화자 안내** 입력 목록을 표시한다. 각 행은 분석으로 얻은 화자 ID를 고정해 보여 주고, 사용자는 이름·역할·관계를 자유롭게 적을 수 있다.

| 표시 | 입력 예시 | 사용 방식 |
|---|---|---|
| `화자 1` | `김민수 · 프로젝트 매니저` | LLM이 발언 맥락을 이해하기 위한 입력 힌트 |
| `화자 2` | `이서연 · 개발 담당` | LLM이 기술 용어와 발언 맥락을 이해하기 위한 입력 힌트 |

입력한 이름과 역할은 LLM 요청에만 쓰는 보조 정보다. AI에는 `화자 1 → 김민수 · 프로젝트 매니저`처럼 별도 대응표로 전달하지만, 이 대응표·이름·역할을 결과 화면이나 Markdown 문서에 자동으로 표시하지 않는다. 원본 전사 메시지와 다듬은 대화의 화자 표기는 모두 `(화자 1)`처럼 유지한다. 따라서 이름을 잘못 입력했거나 AI가 응답 오류를 내도 원본 화자 구간·시간 연결·표시 형식은 변하지 않는다.

### 3.4 GUI와 로컬 웹 화면

- **데스크톱 GUI:** 현재 TalkTracker 창에서 파일 선택, 분석, 로컬 AI 연결, 결과 선택, 저장까지 사용한다.
- **로컬 웹 화면:** TalkTracker가 시작한 웹 서버의 `127.0.0.1` 주소를 브라우저에서 열어 같은 흐름을 사용한다. 웹 화면에서도 음성 파일 선택부터 분석과 AI 정리까지 수행할 수 있다.
- **공통 작업 상태:** 어느 화면에서 작업을 시작해도 다른 화면에는 같은 진행 상태와 결과가 보인다. 같은 분석 엔진을 두 번 돌리지 않도록 한 번에 하나의 분석 또는 AI 정리 작업만 실행한다.
- **로컬 한정:** 웹 서버는 기본적으로 `127.0.0.1`에만 바인딩한다. 같은 네트워크의 다른 기기나 인터넷에서는 접근할 수 없으며, 이 범위는 별도 요구가 있을 때만 검토한다.
- **웹 API 보호:** 웹 화면과 API는 같은 로컬 주소에서만 제공하고, 다른 웹사이트가 API를 호출할 수 있도록 하는 CORS 설정은 넣지 않는다.
- **기록 없음:** 브라우저를 열어도 이전 서버 작업·AI 요청 목록은 표시하지 않는다. 현재 실행 중인 작업과 아직 저장하지 않은 현재 결과만 확인할 수 있다.

## 4. 처리 구조

```text
GUI 화면 ─┐
          ├─ 공통 작업 관리자
웹 화면 ──┘    ├─ 음성 분석 엔진
               └─ 로컬 LLM 정리 엔진

음성 분석 결과
  ├─ 원본 화자 구간·시간·전사문 (변경하지 않음)
  ├─ 사용자가 선택한 결과와 대화의 목적·배경·화자 안내
  ├─ 전체 전사를 우선 LLM에 전달
  │    └─ 컨텍스트 한도 오류일 때만 절반씩 재분할
  ├─ 각 성공 묶음 다듬기 요청 (순차 처리)
  │    └─ OpenAI 호환 로컬 서버
  ├─ 응답 검증·원본 구간 순서대로 재결합
  ├─ 묶음별 요약 재료 생성
  └─ 요약 재료를 단계적으로 합쳐 최종 요약 생성
       ├─ 화면: 사용자가 고른 결과 항목
       └─ 저장: 선택한 Markdown 결과 문서
```

### 4.1 원본 보존 원칙

원본 `화자`, `시작 시각`, `종료 시각`, `원본 문장`은 불변 데이터로 둔다. 원본 전사 메시지는 `(화자 N)` 표기로 출력한다. 사용자가 입력한 화자 이름·역할은 현재 AI 요청에만 쓰며 결과 데이터나 저장 문서에는 넣지 않는다. AI 결과는 원본 구간 ID에 연결된 `다듬은 문장`과 별도 요약으로만 저장한다.

다듬은 대화도 같은 구간 ID·시간·`(화자 N)` 순서로 출력한다. 이 원칙 덕분에 사용자는 원본 전사 메시지와 다듬은 대화를 비교해 AI가 바꾼 문장을 확인할 수 있으며, 요약에서는 대화 전체가 어떻게 압축됐는지 볼 수 있다. AI 연결 오류·중단·형식 오류가 있어도 기존 전사 결과를 잃지 않는다.

### 4.2 전체 우선·문맥 한도 재분할

처음에는 선택한 결과를 만들기 위해 **전사 전체를 한 번에** 전달한다. 선택한 모델의 문맥이 충분하다면 이 경로가 문장 연결과 전체 요약 품질에 가장 유리하다.

서버가 `context length`, `maximum context`, `too many tokens`, `input too long` 등 문맥 한도를 나타내는 오류를 반환하면, TalkTracker가 자동으로 다음 순서를 반복한다.

1. 실패한 전사 묶음을 화자 발화 경계와 가까운 지점에서 절반으로 나눈다.
2. 앞 절반과 뒤 절반을 각각 다시 요청한다.
3. 절반 중 하나도 문맥 한도로 실패하면 그 절반을 다시 둘로 나눈다.
4. 성공한 묶음은 그대로 보관하고, 실패한 묶음만 더 작게 나눈다.

즉, `전체 → 2개 → 4개 → 8개`처럼 필요한 경우에만 입력량을 줄인다. 문장 중간을 자르지 않도록 분할점은 가장 가까운 화자 구간 경계로 옮긴다. 더 이상 나눌 수 없는 작은 묶음도 실패하면 그 묶음은 원본을 유지하고 실패 사유를 결과에 남긴다. 연결 오류·인증 오류·사용자 취소처럼 문맥 길이와 무관한 오류에서는 재분할하지 않는다.

화면에는 전체 전송을 시도했다는 사실과, 재분할되면 현재 분할 수·완료 수를 바로 표시한다. 예: `입력이 길어 4개 구간으로 나누어 전달 중 · 2/4 완료`.

각 묶음에는 대화의 목적·배경 안내, 화자 ID별 이름·역할 대응표, 필요한 최소한의 직전 문맥을 읽기 전용으로 덧붙인다. LLM이 수정 대상으로 돌려주는 것은 해당 묶음의 구간 ID뿐이다. 사용자에게 토큰 수나 분할 크기를 설정하게 하지 않는다.

### 4.3 여러 응답을 하나의 결과로 합치기

다듬은 대화를 선택했다면, 성공한 묶음의 `segment_id`별 다듬은 문장을 원본 시간 순서로 다시 연결한다. 사용자에게는 여러 조각이 아니라 하나의 **다듬은 대화**로 보여 준다.

요약을 선택했다면, 각 묶음에서 사용자에게 보이지 않는 요약 재료를 먼저 만들고 이를 모아 최종 요약을 만든다. 최종 요약 요청도 문맥 한도로 실패할 수 있으므로, 요약 재료 자체를 같은 절반 재분할 규칙으로 단계적으로 합친다. 이 과정을 거쳐도 사용자는 하나의 **요약**만 받는다.

따라서 전체 전송이 성공한 경우에는 한 번의 응답에서, 전체 전송이 길어 실패한 경우에는 여러 내부 요청을 합친 뒤, 사용자가 선택한 결과 항목을 한 화면에서 함께 받는다.

### 4.4 요청 형식과 검증

다듬기 요청은 사람이 읽는 본문만 받는 대신, 응답은 엄격한 JSON으로 받는다.

```json
{
  "segments": [
    {
      "segment_id": "s-0012",
      "refined_text": "네, 다음 주까지 초안을 준비하겠습니다."
    }
  ],
  "chunk_summary": "초안 준비 일정과 담당자를 논의했다."
}
```

요약 요청도 `overview`, `key_points`, `decisions`, `action_items`, `open_questions`처럼 고정된 JSON 필드를 사용한다. 각 항목이 대화에서 확인되지 않으면 억지로 만들지 말고 빈 목록으로 돌려주도록 지시한다. 다듬은 대화나 요약을 선택하지 않았다면 해당 결과를 요청하지 않는다.

응답을 받으면 다음을 검사한다.

- 요청한 구간 ID가 빠지거나 새 ID가 생기지 않았는가
- 화자와 시간 정보가 응답으로 바뀌지 않았는가
- 필수 JSON 구조와 문자열 길이가 유효한가
- 형식 오류 또는 모델의 설명 문구가 섞였을 때 JSON만 안전하게 추출할 수 있는가

검증에 실패한 구간은 원본 텍스트를 유지하고, 전체 결과에 실패 구간 수를 보여 준다. 임의의 문장을 추정해 채우지 않는다.

### 4.5 프롬프트 원칙

시스템 지시는 다음 제한을 분명히 한다.

- 주어진 전사와 문맥만 사용하며 외부 사실을 보태지 않는다.
- 사용자가 입력한 대화의 목적·배경 안내와 화자 이름·역할은 용어와 맥락을 이해하는 보조 정보로만 사용하고, 전사문에 없는 사실의 근거로 쓰지 않는다.
- 화자 이름·역할 대응표는 응답에 다시 출력하지 않는다. 원본과 다듬은 대화의 화자 표기는 항상 `(화자 N)`으로 유지한다.
- 발화의 의미를 바꾸지 않고, 문장부호·띄어쓰기·명백한 인식 오류만 조심스럽게 바로잡는다.
- 확신할 수 없는 단어는 추측으로 바꾸지 않는다.
- 화자명, 시간, 구간 ID를 만들거나 바꾸지 않는다.
- 요약의 결정·할 일·질문은 전사문에서 근거를 찾을 수 있을 때만 적는다.
- 지정한 JSON 이외의 설명을 출력하지 않는다.

프롬프트와 JSON 형식은 코드에서 버전으로 관리한다. 저장 결과에는 사용한 모델 이름, 프롬프트 버전, 완료·중단 상태만 남기며 API 키나 서버 인증 정보는 절대 넣지 않는다.

## 5. 화면 구성

기존 GUI의 단순한 흐름을 유지하고, 웹 화면에도 같은 항목·문구·상태를 제공한다.

| 위치 | 공통 요소 | GUI와 웹에서의 동작 |
|---|---|---|
| 상단 상태 영역 | `로컬 AI 연결 필요` 또는 `로컬 AI 연결됨 · 모델명` | GUI에서는 연결 창, 웹에서는 연결 패널을 연다. |
| 연결 설정 | 서버 주소, API 키, 모델 불러오기, 모델 선택, 연결 확인 | 서버는 사용자가 별도로 실행한다는 안내와 오류 원인을 동일하게 표시한다. |
| 분석 결과 영역 | 결과 항목 선택: `원본 전사 메시지`, `다듬은 대화`, `요약` | 하나 이상 고르며, AI 결과를 고를 때만 배경·화자 안내와 AI 실행 버튼을 보여 준다. |
| AI 정리 영역 | 대화의 목적·배경 안내와 화자 안내 | 자세히 적을수록 품질이 좋아진다는 안내와 예시를 함께 표시한다. 화자 안내에는 분석된 화자마다 이름·역할을 적을 수 있다. |
| 결과 보기 | 선택한 항목 전환 | 원본 전사 메시지와 다듬은 대화는 동일한 `(화자 N)`·시간·순서로 표시해 비교할 수 있으며, 요약은 전체 내용을 압축해 보여 준다. |
| 처리 중 | 전체 전송/재분할 상태, 구간 진행 수, 경과 시간, 중단 버튼 | 문맥 한도로 나뉜 경우 분할 수와 완료 수를 표시하고, 중단 후에도 원본과 완료된 구간을 유지한다. |

연결이 없을 때에도 파일 선택, 분석, 타임라인, 원본 결과 저장은 두 화면에서 동일하게 사용할 수 있다.

## 6. 구현 구성

예상 모듈은 다음과 같다.

| 파일 또는 영역 | 책임 |
|---|---|
| `src/talktracker/core/llm_client.py` | OpenAI 호환 서버 URL 검증, 모델 목록 조회, 스트리밍 채팅 요청, 취소와 오류 변환 |
| `src/talktracker/core/llm_config.py` | 로컬 연결 설정 저장·로드, API 키 비저장 규칙 |
| `src/talktracker/core/refinement.py` | 전체 우선 요청, 문맥 한도 재분할, 프롬프트 구성, JSON 검증, 다듬은 결과·요약 재결합 |
| `src/talktracker/core/workflow.py` | GUI와 웹이 함께 쓰는 분석·AI 정리 작업 관리자, 단일 작업 잠금, 상태·취소·결과 전달 |
| `src/talktracker/core/analysis.py` | 분석 결과 데이터에 사용자가 선택한 원본·AI 결과를 선택적으로 연결 |
| `src/talktracker/main.py` | 데스크톱 GUI: 연결 창, 상태 표시, 결과 전환, 진행·중단 처리 |
| `src/talktracker/web/` | 로컬 웹 서버 API와 정적 웹 화면: 파일 선택, 상태 갱신, AI 정리, 결과 보기·저장 |
| `requirements.txt` | HTTP 스트리밍과 로컬 웹 서버에 필요한 최소 의존성만 추가 |
| `scripts/windows/Install-Dependencies.ps1` | 추가 패키지가 생길 때만 기존 가상 환경 설치 흐름에 포함 |
| `scripts/windows/Run-Web.ps1` | 로컬 웹 서버를 `127.0.0.1`에 시작하고 브라우저 주소를 안내 |

HTTP 클라이언트는 OpenAI SDK의 특정 서버 동작에 의존하지 않고, 참고 프로젝트처럼 OpenAI 호환 엔드포인트를 직접 호출한다. Python에서는 취소와 스트리밍 처리가 쉬운 경량 HTTP 클라이언트를 사용하되, 의존성은 하나로 제한한다.

## 7. 단계별 구현 순서

### 1단계 — 공통 작업 기반과 연결 만들기

**상태: 구현 완료**

- 공통 OpenAI 호환 연결 모듈, 비밀정보를 저장하지 않는 사용자 설정, GUI 연결 창과 웹 연결 패널을 추가했다.
- 웹 화면과 데스크톱 화면은 같은 연결 검증 규칙(로컬 주소 제한, 모델 목록, 짧은 생성 확인)을 사용한다.
- 2단계의 전사 다듬기·요약 작업 실행, 결과 선택 화면은 아직 넣지 않았다.

- 로컬 주소만 받는 연결 설정과 메모리 전용 API 키 처리
- `/v1/models` 모델 목록 조회와 수동 모델 ID 입력 보조
- 짧은 연결 확인 요청, 이해하기 쉬운 오류 표시
- 서버 URL 정규화와 API 키 미저장 단위 테스트

완료 기준: 서버가 실행되지 않았을 때와 실행 중일 때를 두 화면에서 명확히 구분하고, 키가 디스크에 남지 않는다.

### 2단계 — 결과 선택과 짧은 전사 다듬기

- GUI와 웹이 함께 쓰는 AI 정리 작업 상태·취소·단일 작업 잠금 구현
- 원본 분석 결과와 AI 결과의 데이터 구조 분리
- 원본 전사 메시지·다듬은 대화·요약 중 하나 이상을 고르는 화면
- 대화의 목적·배경 안내와 화자별 이름·역할 입력, 품질 안내 문구
- 한 묶음 전사를 JSON으로 다듬는 프롬프트·검증기 구현
- 원본/다듬은 대화 전환 화면과 실패 시 원본 유지

완료 기준: 짧은 녹음에서 선택한 항목만 GUI와 웹에 동일하게 표시되고, 화자·시간은 그대로 둔 다듬은 문장이 별도 표시된다.

### 3단계 — 긴 전사 재분할과 요약 재결합

- 먼저 전체 전사를 보내고 문맥 한도 오류일 때만 절반씩 나누는 재시도
- 분할 수·완료 수를 알리는 순차 생성과 중단 처리
- 묶음별 요약 재료와 하나의 최종 요약을 만드는 단계적 재결합
- 중단·일부 실패·잘못된 JSON에 대한 안전한 결과 처리

완료 기준: 1시간 이상 전사도 먼저 전체 문맥을 활용하고, 한도에 걸리면 필요한 묶음만 재분할하며, 사용자에게는 하나의 다듬은 대화와 하나의 요약을 제공한다.

### 4단계 — 웹 화면과 저장·품질 검증

- `127.0.0.1` 전용 웹 서버와 웹 화면 구현, GUI와의 진행 상태 동기화
- Markdown 결과에 사용자가 선택한 원본 전사 메시지, 다듬은 대화, 요약과 AI 처리 상태를 구분해 저장. 화자 이름·역할 대응표와 배경 안내 입력값은 포함하지 않음
- 연결 오류, 느린 응답, 취소, 모델이 JSON 형식을 어긴 경우의 회귀 테스트
- 실제 로컬 LLM 서버와 짧은 파일·긴 파일 각각으로 수동 검증

완료 기준: GUI와 웹에서 같은 현재 작업·결과를 확인할 수 있고, 저장 문서만 열어도 사용자가 선택한 결과와 AI 처리 완료 여부를 구분할 수 있다.

## 8. 검증 항목

- 같은 PC와 신뢰하는 사설망의 OpenAI 호환 서버 주소를 연결할 수 있고, 인증정보·쿼리·조각 식별자가 있는 URL은 거부하는지
- 웹 서버가 `127.0.0.1`에만 바인딩되고 다른 기기에서 접근할 수 없는지
- GUI 또는 웹 중 한 곳에서 시작한 작업이 다른 화면에도 같은 상태로 보이며, 동시에 두 작업이 시작되지 않는지
- API 키가 설정 파일·저장 Markdown·오류 메시지에 나타나지 않는지
- `/v1`이 있거나 없는 서버 주소 모두 올바른 엔드포인트를 만드는지
- 모델 목록 조회 실패, 연결 거부, 인증 실패, 응답 지연을 각각 구분해 안내하는지
- 취소가 현재 LLM 요청을 중단하고 기존 전사 결과를 보존하는지
- 원본 전사 메시지, 다듬은 대화, 요약 중 하나 또는 여러 항목을 선택해 결과를 만들 수 있는지
- 대화의 목적·배경 안내와 화자별 이름·역할이 각 요청에 들어가되, 전사에 없는 사실을 결과로 만들지 않도록 하는지
- 화자 안내를 입력해도 원본 화자 ID·화자 구간·시간이 바뀌지 않고, 원본 전사 메시지와 다듬은 대화에는 `(화자 N)`만 표시되는지
- 화자 이름·역할 대응표와 대화의 목적·배경 안내가 결과 화면·Markdown 문서에 자동으로 출력되지 않는지
- 화자 수·화자 이름·시간 구간·원본 전사문이 AI 실행 전후로 변하지 않는지
- 잘못된 JSON, 누락·중복 구간 ID, 지나치게 긴 응답을 안전하게 거부하는지
- 전체 전사 요청이 문맥 한도 오류일 때만 `전체 → 절반 → 절반의 절반` 방식으로 재시도하는지
- 재분할한 긴 전사도 순서와 구간 연결이 유지되고, 다듬은 대화와 요약이 각각 하나로 합쳐지는지
- Markdown 저장본에 사용자가 선택한 항목과 중단·실패 상태가 명확히 드러나는지
- 같은 현재 작업을 GUI와 웹에서 열었을 때 원본·다듬은 대화·요약·진행 상태가 동일하게 보이는지

## 9. 결정이 필요한 사항

구현을 시작할 때 다음 두 항목만 실제 사용 환경을 보며 확정한다.

1. 사용할 로컬 LLM 서버와 모델: TalkTracker는 OpenAI 호환 API를 기준으로 연결하므로, 사용 중인 서버에서 모델 목록 조회와 스트리밍 응답이 되는지 먼저 확인한다.
2. 다듬기 강도: 처음에는 보수적으로 문장부호·띄어쓰기·명백한 오인식만 바로잡는다. 고유명사나 기술 용어를 적극 교정하는 사전 기능은 실제 결과를 본 뒤 별도 단계로 추가한다.

그 외 흐름은 사용자가 복잡한 처리 옵션을 고르지 않도록 기본값으로 고정한다.
